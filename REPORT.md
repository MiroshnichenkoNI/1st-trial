# Обработка видео: DOVER и Qwen

Для каждого видео вычисляются техническая и эстетическая оценки DOVER и текстовое описание Qwen3-VL-2B-Instruct. Два режима используют одинаковые веса, подготовку входов и параметры генерации. Различается порядок подачи работы моделям.

## Два решения

### Baseline: фиксированные группы

Видео объединяются в группы по четыре. Сначала DOVER последовательно оценивает все видео группы, затем четыре запроса передаются Qwen. Следующая группа допускается к моделям после завершения всей текущей группы. Пока GPU работает, один фоновый поток CPU готовит входы следующей группы.

Такое расписание даёт понятную точку сравнения и уже использует библиотечный батчинг vLLM. Его ограничение — ожидание последнего ответа группы: завершившиеся запросы не заменяются новыми, пока не закончится самый долгий.

### Optimized: пополнение по готовности

Поддерживается до четырёх активных запросов Qwen. Когда один завершается, освободившееся место может занять следующее подготовленное видео. Для него сначала вычисляется DOVER, после чего запускается Qwen. CPU заранее готовит до двух следующих видео; DOVER может выполняться, пока Qwen обрабатывает предыдущие запросы.

Это уменьшает ожидание на границах групп. Оба режима используют AsyncLLM, а объединением запросов и выполнением модели управляет vLLM. Четыре активных запроса — верхний предел, а не постоянный размер вычислительного батча. Обе модели работают на одной V100, поэтому конкуренция за её ресурсы ограничивает выигрыш от перекрытия.

## Настройки моделей

### DOVER

Используются официальные веса и настройки подготовки кадров. Для технической и эстетической ветвей формируются разные представления одного видео; необходимые обеим моделям кадры извлекаются совместно через PyAV. Выходы каждой ветви усредняются отдельно.

DOVER работает в FP32, в режиме оценки и без расчёта градиентов. Смешанная точность и TF32 отключены: в этом сравнении численную точность DOVER не меняли. Возвращаются сырые оценки модели; отрицательные значения допустимы, это не проценты качества. Две ветви следует рассматривать отдельно.

### Qwen

Используется Qwen3-VL-2B-Instruct в FP16, без дополнительного квантования в FP8/INT8/4 бита. Модель целиком размещена на одной GPU. FP16 выбран для V100; нативной поддержки BF16 у неё нет.

Запрос: «Сгенерируй детальное описание всего, что происходит на видео». Модель получает выбранные кадры и сведения об их времени; звук не подаётся.

| Настройка | Значение и смысл |
|---|---|
| Кадры | Около 2 кадров в секунду, равномерно по ролику. Число кадров округляется до чётного для видеопроцессора. |
| Объём видео | До 8 388 608 пикселей суммарно на выбранные кадры одного видео. Ограничивает размер входа и расход памяти. |
| Длина ответа | До 768 новых токенов. Модель может закончить раньше; достижение лимита отмечается как `length`. |
| Выбор следующего токена | `temperature=0.7`, `top-k=20`, `top-p=0.8`: генерация остаётся случайной, но выбор ограничен более вероятными продолжениями. |
| Штраф за повторы | Из оценки токена вычитается 1.5, если он встречался среди последних 256 токенов промпта и ответа. Это снижает недавние повторы. |
| Случайность | `seed=42`. Фиксирует начальное состояние генератора, но не гарантирует одинаковый текст при другом составе батча и порядке вычислений. |
| Контекст | До 8192 токенов на запрос вместе с ответом. Бюджет обработки токенов за шаг vLLM также ограничен 8192. |
| Параллельные запросы | Не более четырёх. Модель не разделяется между несколькими GPU. |
| Память | Бюджет vLLM — 60% памяти GPU; оставлен запас для DOVER и промежуточных данных. Это настройка бюджета, а не измеренная постоянная занятость. |
| Кеширование | Повторное использование общего префикса между запросами и кеш мультимодального процессора отключены. Каждый повтор видео заново проходит подготовку и модели. |

В обоих режимах разрешены компиляция и CUDA Graphs, сокращающие расходы на повторный запуск GPU-операций. Асинхронная подача запросов через AsyncLLM используется при выключенной отдельной настройке `async_scheduling`. На CPU работает один подготовщик; внутренним операциям PyTorch и декодеру разрешено четыре потока.

## Что пробовали до этого

Это отдельные исследовательские серии на Mac и CUDA. Их результаты не объединяются с текущим сравнением на V100.

| Попытка | Результат |
|---|---|
| DOVER на CPU и подготовка следующих видео на Mac | Получено ускорение всего конвейера в локальных сравнениях. Описания сохранялись; оценки DOVER имели небольшие численные отличия. |
| Последовательное декодирование через OpenCV | Получение кадров ускорилось при совпадении кадров и результатов. Ускорение всего конвейера не подтвердилось. |
| Увеличение GPU-батча DOVER на Mac | Обработка замедлилась; крупный батч усиливал давление на память и использование swap. |
| Статический и динамический батчинг Qwen в MLX | Проверенные варианты меняли часть описаний, давали замедления и рост потребления памяти. Рабочий режим ими не заменили. |
| Пакетная обработка attention в зрительной части Qwen | Зрительный энкодер ускорился в микробенчмарке с сохранением выходов. Устойчивый выигрыш всего конвейера не установлен. |
| Зрительная часть Qwen через Core ML параллельно с языковой частью через MLX | В гибриде с Core ML для части видео и фиксированной длиной ответа получено ускорение на полном потоке. Эквивалентность описаний и фактическое исполнение на ANE не подтверждены. |
| Гибкие размеры входов Core ML | Вариант заработал на разных видео, но проверенный гибрид оказался медленнее; в итоговый CUDA-вариант не вошёл. |
| Более высокая точность отдельных операций Core ML | Перенос начальной проекции кадров в FP32 уменьшил расхождение признаков, но численные критерии полностью не выполнены. Исправление ошибок описаний не подтверждено. |
| Многопоточный декодер и предварительная подготовка Qwen на CUDA | Исторические проверки показали ускорение подготовки и прохода с сохранением проверенных ответов. Эти приёмы используются и сейчас. |
| Прямая передача CPU-входов и настройка `async_scheduling` | В отдельных проверках убедительного выигрыша не дали. |
| Prefetch и непрерывное пополнение запросов vLLM | Prefetch ускорял серию с сохранением ответов. Пополнение очереди повышало throughput, но меняло часть текстов и могло увеличивать задержку отдельного запроса. |
| Перераспределение свободной GPU-памяти между DOVER и Qwen | Первые варианты не помещались в память. Освобождение кешей позволило завершить серию, но убедительного преимущества перед обычной групповой схемой не дало. |
| DOVER следующей группы и NVIDIA MPS | Фоновый DOVER не ускорил проверенную групповую схему. MPS работал, но преимущества над историческим непрерывным режимом не доказал. |
| Переход с ручного управления шагами vLLM на AsyncLLM | Полные проходы завершились, время практически совпало. Сам переход на AsyncLLM не показал самостоятельного ускорения. |
| Общий набор зависимостей для DOVER и Qwen | Оба режима заработали в одном окружении. Смена версий библиотек изменила часть токенов промпта и немного оценки DOVER; результаты старого стека не считались идентичными. |

Профилирование CPU/CUDA использовалось для поиска пауз в подготовке, передаче данных и выполнении моделей. Скорость измерялась отдельно от запусков под профайлером.

## Текущий замер

12 ноября 2026 года, Tesla V100 PCIe 32 GB. Один Python-стек: PyTorch 2.9.0, Transformers 4.57.1, vLLM 0.11.2. Чистая установка в пустую `.venv` прошла; использовался кеш wheel-файлов. Проверки зависимостей и контрольных сумм весов успешны.

Выполнена одна пара запусков: baseline и optimized. В каждом — 10 видео прогрева и 50 рабочих заданий, то есть пять повторов набора. Основная метрика — время между 12-м и 32-м завершениями: 20 результатов, каждое видео дважды. Загрузка моделей и прогрев исключены; несбалансированное окно отклоняется.

| Режим | Окно 20 видео, с | Видео/мин | Токенов в окне | Все 50 видео, с |
|---|---:|---:|---:|---:|
| Baseline | 70,833 | 16,94 | 5205 | 188,704 |
| Optimized | 66,370 | 18,08 | 4949 | 170,215 |

В этой паре throughput вырос на **6,72%**, время окна сократилось на **6,30%**. В optimized сгенерировано на 4,92% меньше токенов в окне; разница включает влияние длины ответов. Одна пара не устанавливает повторяемость ускорения или статистическую значимость.

Замер выполнен до последних правок кода. Расчёт метрики перепроверен на сохранённых результатах; повторного запуска моделей не было.

Обычный запуск на десяти видео занял 39,441 с рабочего времени и сгенерировал 2490 токенов. Все 140 результатов обычного запуска и benchmark, включая прогрев, завершились по `stop`, без пустых ответов. После завершения GPU вернулась к исходной занятости, вычислительных процессов не осталось.

## Оценки и описания

Все 280 значений DOVER в проверенных 140 результатах точно совпали с предыдущей версией на тех же файлах. Восемь из десяти описаний обычного прохода совпали дословно; изменились №4 и №6. Тексты могут различаться между повторами и режимами при одинаковых настройках.

Известные ограничения Qwen сохранились: встречаются ошибочные объекты, неподтверждённые действия и пропущенные детали. В №6 окорок назван пирожным, в №10 шмель — бабочками; №5 описан на английском при русском запросе. Улучшение качества ни одному режиму не приписывается. Проверка содержания выполнена по восьми кадрам каждого ролика, а не по полной эталонной разметке.

Свежие результаты находятся в `results/videos.jsonl`, оба benchmark-прогона и сравнение — в `results/benchmark/`. Проверка чисел сохранена в `results/validation.json`, разбор описаний — в `results/quality_review.json`.

## Дальнейшие ускорения

При большом бюджете ресурсов приоритеты следующие. Это направления для проверки, а не уже измеренный эффект текущего решения.

1. **Более быстрые GPU и несколько реплик.** Сначала перенести модели на GPU с большей вычислительной мощностью и пропускной способностью памяти. Для большого потока запускать независимые копии моделей на нескольких GPU и распределять видео через общую очередь. Масштабирование продолжать, пока ограничением не станут CPU, хранение или сеть.
2. **Раздельные ресурсы для моделей.** Выделить DOVER и Qwen отдельные GPU или пулы GPU, чтобы они не конкурировали за память и вычисления. Число копий каждой модели подбирать по скорости её стадии; учитывать стоимость передачи данных между стадиями.
3. **Более плотная загрузка Qwen.** Подбирать число одновременно активных запросов и объединять видео близкого размера и числа кадров. Это уменьшает ожидание из-за неодинаковых входов. Контролировать память и задержку отдельного видео: максимальный throughput не всегда даёт самый быстрый единичный ответ.
4. **Пониженная точность.** Для Qwen проверить FP8/INT8, затем 4-битные веса на поддерживаемых GPU; для DOVER — смешанную точность вместо FP32. Выигрыш зависит от доступных вычислительных ядер. После каждого изменения сравнивать оценки и фактическое содержание описаний. BF16 может помочь численной устойчивости, но не экономит память относительно FP16 и не гарантирует улучшения качества; V100 его нативно не поддерживает.
5. **Чтение и декодирование.** Если GPU простаивает в ожидании кадров, использовать более быстрые диски, предварительное чтение и аппаратный декодер. Число подготовщиков увеличивать по замеру, чтобы не переполнить RAM. Сохранять выбранные кадры и преобразования: смена декодера не должна незаметно менять вход модели.
6. **Повторное использование постоянной работы.** Кешировать токенизацию неизменяемого текста и частей шаблона. Для короткого запроса ожидаемый эффект небольшой. Одинаковая инструкция стоит после видео, поэтому сама по себе не даёт одинакового префикса для кеша вычислений модели. Готовые описания и оценки повторяющихся видео в таком benchmark переиспользовать нельзя: каждый повтор должен выполнять обе модели.

Уменьшение числа кадров, разрешения или длины ответа также может ускорить обработку, но меняет объём информации и подробность результата. Такие варианты требуют отдельного сравнения качества и не должны смешиваться с ускорениями при прежней задаче.
