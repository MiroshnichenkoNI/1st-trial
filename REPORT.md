# Обработка видео: DOVER и Qwen

**Пайплайн.** Для каждого видео DOVER вычисляет техническую и эстетическую оценки, Qwen3-VL-2B-Instruct формирует описание. Для уменьшения повторов добавлен штраф: перед выбором следующего токена его логит уменьшается на 1,5, если этот токен встречался в последних 256 позициях промпта и сгенерированного ответа. В проверочном запуске без штрафа 4 из 10 описаний зациклились на повторяющихся фразах и достигли лимита 768 токенов. Модели загружаются один раз и работают на одной GPU. Обработка состоит из трёх этапов:

1. **Подготовка на CPU.** Через PyAV считываются кадры, необходимые обеим моделям. Из общих декодированных кадров отдельно формируются входы DOVER и Qwen. Один фоновый поток заранее готовит следующие входы, пока GPU обрабатывает текущие.
2. **Оценка DOVER.** Модель получает выбранные фрагменты видео и за один вызов возвращает две оценки. После этого подготовленный вход передаётся Qwen.
3. **Описание Qwen.** Визуальный энкодер преобразует кадры в признаки, затем языковая часть обрабатывает вход и генерирует ответ по токенам. Запросы передаются через AsyncLLM; вычисления и батчинг выполняет vLLM 0.11.2.

**Два режима обработки.** Модели, выбор кадров и настройки генерации одинаковые; отличается порядок подачи работы.

- **Baseline:** видео поступают группами до четырёх. DOVER последовательно оценивает все видео группы, затем их запросы отправляются Qwen. Следующая группа начинает обработку на GPU только после завершения всех описаний предыдущей. Кадры следующей группы подготавливаются заранее в фоновом потоке CPU.
- **Optimized:** видео поступают по одному; одновременно допускается до четырёх незавершённых запросов Qwen. После освобождения места следующее видео проходит DOVER и поступает Qwen без ожидания остальных описаний. В очереди подготовки на CPU предусмотрен запас из двух заданий. Новый запрос добавляется по готовности входа и оценок DOVER, поэтому число активных запросов может быть меньше четырёх.

**Параллелизм.** В обоих режимах vLLM использует continuous batching: формирует общий батч для очередного шага языковой модели и хранит отдельный KV-cache каждого запроса. Завершившиеся запросы удаляются из батча. Optimized позволяет пополнять его новыми запросами без ожидания всей группы.

Подготовка на CPU перекрывается с вычислениями на GPU. В optimized вызов DOVER для следующего видео также может выполняться, пока запросы Qwen ещё не завершены. DOVER вызывается в фоновом потоке основного процесса, Qwen работает в отдельном процессе vLLM. Это не гарантирует одновременного исполнения их GPU-ядер. Копии Qwen и разделение модели между несколькими GPU не используются.

Визуальная обработка нового запроса выполняется перед соответствующим языковым проходом и может увеличить интервал между токенами уже обрабатываемых запросов. Continuous batching не устраняет эту задержку.

Для совместной работы DOVER и Qwen на одной GPU также проверялся NVIDIA MPS. В проведённой проверке прироста скорости он не дал.

**Настройки моделей.**

- **DOVER:** официальные веса и подготовка входов, FP32.
- **Qwen:** FP16, около двух кадров в секунду, бюджет 8 388 608 пикселей на видео. Запрос: «Сгенерируй детальное описание всего, что происходит на видео». Звук не используется.
- **Генерация:** максимум 768 новых токенов; `temperature=0.7`, `top-p=0.8`, `top-k=20`, `seed=42`. Штраф 1.5 применяется к токенам из последних 256 позиций промпта и ответа.
- **vLLM:** контекст до 8192 токенов, до четырёх запросов, бюджет 60% памяти GPU (чтобы dover влез). Кеширование общего префикса отключено.

V100 не поддерживает нативные BF16-вычисления, поэтому сейчас Qwen использует FP16.

**Результаты.** Замер выполнен на Tesla V100 32 GB: один запуск baseline и один optimized. После прогрева каждый обрабатывал 50 видео — пять повторов набора. Сравнивалось время между 12-м и 32-м завершениями: каждое видео попадало в окно дважды.

| Режим | Время окна из 20 видео | Пропускная способность в окне, видео/с | Полное время 50 видео |
|---|---:|---:|---:|
| Baseline | 70,833 с | 0,282 | 188,704 с |
| Optimized | 66,370 с | 0,301 | 170,215 с |



**Потенциально высокое влияние**

1. **Распределение GPU между DOVER и Qwen.** Выделить моделям отдельные GPU и подобрать их количество так, чтобы суммарная пропускная способность двух этапов была сбалансирована. Более быстрому DOVER выделять меньше GPU, чем Qwen.
2. **Разделение визуального энкодера и языковой части между GPU.** Визуальные признаки новых видео вычислять на одной GPU и передавать языковой части на другой, сохраняя continuous batching генерации. Это позволит выполнять визуальную обработку новых видео параллельно с языковыми вычислениями предыдущих.
3. **Подбор batch size.**  Более крупный батч может повышать пропускную способность: удвоение batch size не обязательно удваивает время вычислений. Подбирать значение по скорости потока и памяти 

**Влияние от небольшого до высокого — зависит от нагрузки и реализации**

4. **Оптимизация вычислительных ядер.** Сравнить доступные реализации attention и линейных слоёв, ориентируясь на наиболее затратные операции из профиля.

5.  **Квантизация моделей.** Проверить варианты с меньшей разрядностью, совместимые с моделью, GPU и используемой версией vLLM.
6. **Prefix caching.** При длинном одинаковом префиксе промпта кэшировать результат его обработки — KV-cache. Если для одного видео выполняется много разных запросов, переиспользовать визуальные признаки и KV-cache общей части входа с видео, размещая разные вопросы после неё. Большой эффект ожидается при частом повторении длинного общего входа
